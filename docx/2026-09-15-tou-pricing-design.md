# 峰谷计价 设计与实现说明

> 日期：2026-09-15 · 模块：价目表 / 花费估算（`lib/pricing.js`、`lib/aggregate.js`、`lib/price-editor.js`）
> 版本：`kimi-usage-stats` 1.0.0 → 1.1.0

## 1. 目标与边界

**目标**

- 支持「按不同时段分别计价」：同一条用量记录按其**发生时间**落到对应时段，用该时段单价计费，最后汇总总成本。
- 峰（高峰）与谷（低谷/闲时）分别可见：模型行显示「峰 ¥x · 谷 ¥y」，汇总卡显示全局峰谷合计。
- **完全兼容原有单一计价**：未启用峰谷的模型行为、接口、金额与升级前逐位一致。

**不做**

- 不做跨服务商的自动拉价（仍为内置公开参考价 + 用户手改）。
- 不按请求时长拆分横跨峰谷边界的单条请求（整条按记录时间归属，见「已知取舍」）。
- 不改动扫描/解析口径，不新增网络请求，不新增权限。

## 2. 数据模型

价目条目在原三档价基础上新增可选字段 `periods`：

```js
// 单一计价（原有，完全不改）
{ input, cacheRead, output }

// 峰谷
{
  input, cacheRead, output,        // 基础价：约定为「高峰价」（未命中任何时段的兜底价）
  periods: [                        // 低谷（闲时）窗口列表；先声明者优先
    { kind: 'offpeak' | 'peak',     // 分桶用：peak / offpeak；缺省视为 offpeak
      start: 'HH:mm', end: 'HH:mm', // 左闭右开 [start, end)；start > end 表示跨天
      days: [0..6],                 // 适用日（0=周日）；缺省 = 每天
      input, cacheRead, output }    // 该时段的三档价
  ]
}
```

语义约定：

| 情况 | 行为 |
| --- | --- |
| 条目无 `periods` | 单一计价（全天同价） |
| `periods: []` | **显式停用**峰谷 → 单一计价（不会被内置默认时段覆盖） |
| 条目有 `periods`，时间命中某段 | 用该段单价与 `kind` 分桶 |
| 条目有 `periods`，时间未命中任何段 | 用基础价（高峰），归 `peak` 桶 |

时段匹配为纯函数 `matchPeriod(periods, timeMs)`：半开区间；跨天时「次日凌晨」归属**声明该时段的那一天**（用 `(day+6)%7` 反查），因此 `周一 22:00 → 06:00` 的周二 03:00 仍算周一；非法或零长度时段跳过。

## 3. 计价 API（向后兼容）

| 函数 | 说明 |
| --- | --- |
| `getPrice(model, overrides)` | 不变：返回基础三档价（峰谷条目即高峰价）。老调用方零改动 |
| `calcCost(model, usage, overrides)` | 不变：基础价口径，等价于 `calcCostAt(..., null)` |
| `getPriceEntry(model, overrides)` | 新增：返回有效条目（含 `periods`），用户条目缺 `periods` 时继承内置默认 |
| `resolvePrice(model, overrides, timeMs)` | 新增：按时点取价，返回 `{input, cacheRead, output, kind, label, tou}` |
| `calcCostAt(model, usage, overrides, timeMs)` | 新增：按时点计费；`timeMs=null` 时退化为 `calcCost` |
| `costWithPrice(price, usage)` | 新增：已自行取价时直接计费，避免重复解析 |
| `matchPeriod` / `parseHM` / `normalizeDays` / `describePeriod` | 新增：时段匹配与展示工具 |
| `migratePriceTable(stored, legacy)` | 新增：价目表结构升级迁移 |

## 4. 聚合改造（`lib/aggregate.js`）

关键变化：**由「先合计 token 再套单价」改为「逐条按记录时间取价后累加」**。

- 对单一价模型，两种算法数学等价（线性），故金额与升级前完全一致；
- 对峰谷模型，这才使得同一模型的峰/谷记录各按各的价计。

每行新增：

```js
tiers: { peak: {token, cost}, offpeak: {token, cost}, flat: {token, cost} }, // 分桶
tou: boolean,   // 本行是否有记录按峰谷时段计过价（UI 据此决定是否显示峰/谷拆分）
```

`cost` 语义不变：零用量或全部记录未定价 → `null`（UI 显示 —）。`summarize` 增加 `tier`（全局三桶）与 `tou`；`aggregateBySession`、`interruptStats`、热力图、会话下钻的花费均改为时间感知（会话/中断金额口径与模型表一致）。

## 5. 内置默认（DeepSeek 峰谷）

DeepSeek 自 **2026-08-17 00:00（北京时间）** 起改用峰谷定价：高峰 = 每日 `09:00-12:00` 与 `14:00-18:00`，其余为闲时，闲时单价为高峰的一半。

| 模型 | 高峰 输入/缓存/输出 | 闲时 输入/缓存/输出 |
| --- | --- | --- |
| `deepseek-v4-flash` | 3 / 0.1 / 9 | 1.5 / 0.05 / 4.5 |
| `deepseek-v4-pro` | 9 / 0.3 / 27 | 4.5 / 0.15 / 13.5 |

（单位：元 / 百万 tokens）`periods` 显式声明三段闲时窗口：`00:00-09:00`、`12:00-14:00`、`18:00-00:00`。

> 官方公告未区分工作日与周末，故默认「每天」；若实际计费把周末整天算作闲时，可在价目表把三段改为「周一～周五」（编辑器已支持适用日）。

## 6. 升级迁移

存量用户 IndexedDB 里已有一份由旧默认表播种的价目表，且**覆盖优先于默认**，若不迁移，新内置峰谷时段不会生效。因此：

```js
// store.initPriceTable()
if (存量不存在)  → 用新默认播种，记录 priceTableVersion = 2
else if (版本 < 2) → migratePriceTable(存量) 后写回，版本置 2
```

迁移规则（`migratePriceTable`，纯函数、可单测）：

- 未改动过的行（无 `periods` 且三档价与 v1 内置快照逐一相等）→ 升级为新默认（拿到峰谷时段）；
- 用户改过的行 → 原样保留（含 `periods: []` 这种「显式停用峰谷」）；
- 仅在存量表里出现的行（用户自建模型）→ 保留；
- 仅在内置表里出现、且 v1 快照里没有的行（未来新增模型）→ 补齐默认。

**副作用提醒**：升级后 DeepSeek 的估算金额会变 —— 官方 2026-08-17 起既是调价也是改峰谷制：缓存命中输入 `0.2 → 0.1`（高峰价），未命中输入 `1 → 3`，输出 `2 → 9`。所以**缓存占比高时总额下降、输出占比高时上升**，不是统计口径 bug。

以本机真实数据（1202 个 `wire.jsonl` / 39513 条记录）实测新旧对照：

| 模型 | 旧单一价 | 新峰谷价 | 高峰 / 低谷 |
| --- | --- | --- | --- |
| `deepseek-v4-flash` | ¥138.27 | ¥139.40 | ¥113.86 / ¥25.54 |
| `deepseek-v4-pro` | ¥134.55 | ¥58.54 | ¥52.88 / ¥5.66 |
| `deepseek-v4-flash-vision-exp` | ¥13.36 | ¥9.32 | ¥7.53 / ¥1.79 |
| **DeepSeek 合计** | **¥303.30** | **¥225.41** | — |
| 全部模型合计 | ¥8505.67 | ¥8427.78 | — |

## 7. UI

**价目表弹层**（`dashboard/dashboard.html` + 新增 `lib/price-editor.js`）

- **两行式模型名**：主名用 `config.toml` 的 `display_name`（**与主表显示一致**），次行小字标出**取价键**（`priceKey` 短名）——因为定价与行去重都按短名走，不标出来就无法把价目表的行与主表的模型对应上（典型坑：主表 `K2.8 Preview` 的取价键是 `kimi-for-coding`）。
- 主名后**徽标三态**：`未定价` / `单一价` / `峰谷 N 段`（悬停给出时段摘要）；三档价全空即未定价，不再与「单一价」混为一谈。
- 同短名的多个 config key **共用一行价格**（这是定价按短名的必然结果），此时次行后缀「N 个配置共用此价」，完整 key 列表放进悬停提示。
- 只在记录里出现、没写进 `config.toml` 的模型：主名退回短名 + 「未在配置中」徽标，次行给完整 key。
- 每行：三档基础价 + 「峰谷…」按钮。
- 展开时段区：`类型（低谷/高峰）| 起 | 止 | 输入 | 缓存命中 | 输出 | 适用日（日一二三四五六，可多选）| 删除`；底部 `+ 添加时段`、`套用内置时段`、口径说明。
- 底部新增「恢复内置默认价」：仅覆盖**内置价目表里存在**的模型（自建/未收录模型保持不动，避免一键清空用户填的价），且需再点「保存」才落库。
- 未定价模型三档留空显示 `—`，保存时不会被误写成 0 价（`readPriceTable` 跳过三档与时段全空的模型）。

**模型表 / 汇总卡**

- 模型行：启用峰谷的模型带琥珀色「峰谷」徽标，估算花费下方小字显示 `峰 ¥x · 谷 ¥y`；未启用则不显示该行小字。
- 估算花费卡：`¥总额` 下方一行显示 `峰 ¥x · 谷 ¥y · 单一价 ¥z`（含各时段 token 的 tooltip），并给出全局 `tou` 状态。
- 会话下钻的模型分布表同样给峰谷模型加徽标；面板抽屉底部金额下方补一行峰谷拆分。

### 8.1 用户复审后的修正

用户复审指出「价目表中的模型名与主表不一致」，并采纳了命名方案 A。本章修正如下：

1. **模型名统一**：价目表主名改用 `config.toml` 的 `display_name`，次行小字标出取价键（短名）；同短名多配置共用一行时给出「N 个配置共用此价」，未配置模型退回短名 + 「未在配置中」徽标。（`lib/price-editor.js` + `dashboard.js` 的 `openPriceEditor`）
2. **峰谷拆分只对峰谷行显示**：`dashboard.renderModelView` 的花费单元格原先漏了 `r.tou` 判断，导致单一价模型也显示「峰 ¥0.00 · 谷 ¥0.00」——已修（该缺陷与 8.1 同日发现，属实现未跟上注释意图）。
3. **徽标补「未定价」态**：`syncTou` 原为两态，未定价模型被写成「单一价」——改为三态，并给行加 `input` 监听使徽标随输入实时变化。
4. 修正后 `node --test` 仍为 91/91 通过，并用 headless 渲染复核了 6 行（含共用价提示、未配置徽标、未定价态）。

### 8.2 第二轮复审：术语统一与「套用内置时段」加固

1. **术语：对外一律叫「峰谷」**。原先把「分时」当主称谓，用户要求改为「峰谷」，于是全库面对用户的文案与文档术语统一为「峰谷」（徽标 `峰谷 N 段`、按钮 `峰谷…` / `峰谷 (N)`、价目表列头 `峰谷`、模型表徽标 `峰谷`、README/设计文档标题等）。内部标识符（`periods` / `tier` / `tou` / `syncTou` / `.price-tou`）保持不变——它们描述的是实现（按时间取价的时段表），不影响用户认知，改名只会制造无谓的 diff。
   替换时避开了普通词「分时段」与组合词「峰谷分时」，改完用脚本校验：全库剩余的「分时」只出现在「分时段」中。
2. **「套用内置时段」加固**（原实现有两个隐患）：
   - 该模型在内置价目表里**没有**预置时段时（如 Kimi 系列），点击只会清空用户已有时段却什么都不填 → 现在按钮**置灰**，悬停说明「内置价目表未给该模型配置峰谷时段，没有可套用的内容」。
   - 已有内容时点击会**静默丢弃** → 现在先弹确认「用内置时段覆盖当前的 N 段？」。
   - 语义澄清（按钮 tooltip 也写明）：只覆盖**时段列表**，**不动上方三档基础价**。

### 8.3 布局：加宽容器，消除表格横向滚动条

用户要求「`card table-wrap` 不超出窗口、不出现左右滚动条」，并选定**不压缩行列、只扩展容器**。

实测（headless 渲染真实 CSS + 11 列真实内容）：

- 模型表自然宽 **1121px**（列内容净宽 814 + 列内边距 308，即 14px×2×11 列）；会话表 763px。
- 旧配置 `.container / .hero-inner { max-width: 1180px; padding: 0 28px }`，且 `* { box-sizing: border-box }` → 容器内容只有 1124px、卡片内可用 **1110px < 1121px** ⇒ **任何窗口宽度下都溢出**（1080 屏超 +111，1280/1440/1920 屏均超 +11）。
- 改法：新增布局变量 `--page-max: 1280px`，`.container` 与 `.hero-inner` 共用它（保证横幅与内容区对齐），其余不变。
- 改后实测（模拟窗口宽度 → 模型表溢出）：1080 → +111 ｜ 1160 → +31 ｜ 1180 → +11 ｜ **1190 → 0** ｜ 1200/1280/1920 → 0。即**窗口宽度 ≥ 1190px 时彻底无横向滚动条**；实际 1384px 窗口渲染下横幅与容器均为 1280px、滚动条消失。
- 保留 `.table-wrap { overflow-x: auto }` 作为超窄窗口的兜底：窗口窄于约 1190px 时仍是卡片内滚动（不污染页面级滚动），因为 11 列不压缩时最小宽度 1121px 本身已超过窄窗口宽度。

## 9. 已知取舍

- 单条请求横跨峰谷边界时，整条按**记录完成时刻**（`step.end` 的 `time`）归属，不按时长比例拆分。
- 时段按**本地时区**判断，跨时区使用需自行换算。
- 未定价模型不进任何分桶，也不计入总花费。
- 未收录模型的单价不猜测（如 `deepseek-v4.1-flash` 保持未定价）；带日期后缀的模型（如 `deepseek-v4-flash-0731`）沿用既有前缀兜底，因而自动继承 flash 的峰谷时段。
